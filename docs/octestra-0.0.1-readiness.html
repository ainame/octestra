Core value & release readiness

Octestra: what is it worth, and how far from 0.0.1?

updated 2026-07-30HEAD 20588ee+36 commits / 5 days make all green5 of 6 blockers closed

The value is real and it is concentrated in two places: the maintenance contract that lets a customized workflow still take an upgrade, and the handful of lifecycle correctness details a team would get wrong silently. It is not in agent orchestration, proof rendering, or the config plumbing.

What ships today is the part that matters: a field change becomes an agent run, a pull request, a validation pass, a review request and a merge, repeatable across as many task issues as you open. Running that unattended on a schedule is a later convenience, not a missing pillar — see the correction in section 02.

Readiness: five of six blockers closed. The one-way door is shut, the security scope and the consumer contract are written down, and the only thing left is the end-to-end run — whose result is the one thing that can still add work here.

02 What bounds the value

Two real ceilings, and two claims this report got wrong. The corrections come first, because they move the verdict further than either ceiling does — both in the same direction, upward.

Removing Loops cost no value correction

An earlier version of this report deducted value for the removed Loop subsystem, arguing the setup cost is only repaid by a continuous sweep across many tasks. Two mistakes in one paragraph.

It treated an unshipped roadmap item as a debt against what shipped. An aspiration recorded in TODO.md is not a deficiency in the thing you can install today; scoring it that way double-counts the author's own honesty about future work.

And it conflated "many tasks" with "needs a scheduler". Nothing about running fifty tasks requires one: the EPIC skill opens the sub-issues, a bulk field change starts them, and the per-issue concurrency group serialises each one so a repeated transition queues instead of putting a second agent on the same branch. Throughput at scale is already here.

What a schedule would add is unattended initiation — a capability orthogonal to the state machine, and in implementation terms a cron plus a bounded query over operations that already exist. The open questions in TODO.md §1 are about autonomous task creation, which is a new feature, not the completion of this one.

Issue Fields is load-bearing, not a swappable backend correction

An earlier version of this report suggested putting the state machine's storage behind a seam, so something more widely available could serve instead. That was wrong, and it was wrong because it treated the field as a place to keep state rather than as the thing that starts the run. The substrate has to satisfy three conditions at once:

  • issues: field_added is a repository workflow trigger. The field change is what launches the workflow — a store GitHub emits no repository event for cannot drive anything.
  • Single select, so one task holds exactly one status.
  • The payload carries the previous value (changes.issue_field_value.from.option.name), which is what the transition guard compares against to decide whether the move was legal.

So the organization + admin + new-API requirement really does bound how many teams can adopt this — but as a consequence of how the run is triggered, not as a design choice to revisit. What stays transferable is the idea of the update contract, not a re-hosting of the state machine.

Payoff requires N tasks × time scope

For one agent on one repo occasionally, Octestra is strictly negative: claude-code-action plus thirty lines of YAML wins. The framework only pays where lifecycle state is genuinely hard and the workflow will be revised repeatedly. That's a real ICP — a platform team running migrations across a large repo — but it's narrow, and the README doesn't name it.

Name-addressed statuses are permanent fragility accepted

Renaming a status option in the organization breaks every installation (P1). You investigated the alternative, reverted it, and documented why — the write endpoint gives no ID form. That's the correct disposition, and it's still a footgun every adopter inherits forever.

04 The one-way door — closed

The agent-steps region no longer names a step Octestra must move fixed in d1efc7d

What it was: a region's contents cross an update verbatim, and both agent-steps regions named steps.app-token.outputs.token. Moving agent execution away from the privileged token deletes that step from the agent's job — at which point every installation still carries the old reference, and GitHub resolves it to the empty string, not an error. Markers balanced, doctor green, clean diff, agent running with no credential. This was the only item whose cost rose after release, which is why it went first.

env.OCTESTRA_AGENT_GITHUB_TOKEN    published by a step outside the region
steps.epic.outputs.*               the documented interface
steps.app-token.outputs.token      gone — and now a test failure if reintroduced

Three things landed together: the token is published under a name Octestra owns, each template's header states which symbols a region may reference, and test/install.test.sh fails when a template breaks it. The check anchors its marker match exactly as custom_region_marker in install.sh does — its first version did not, and false-positived on a comment that merely quoted a marker name.

Deprecated aliases dropped done · d1efc7d

The nine bare names protected installations that predate a release, and there is no release. Removing them surfaced a real defect: README.md documented every lifecycle operation by its pre-namespace name, so the table and the prose advertised names that would no longer dispatch. Both now carry lifecycle/.

Security scope stated done

README.md gained a Security section, placed before Installation because it decides whether you should install at all. It says the scope is a private repository with trusted members, that whoever can change the status field can start an agent run and should be treated as having write access, that whoever can edit an issue body decides what the agent is told, and that a passed proof is the validating agent's own claim. It states what is not implemented without promising when it will be.

The consumer contract, as one page done

README.md gained The contract: what you provide, every name Octestra publishes for your steps in each workflow, and a table of rules paired with what breaks when one is ignored — a branch under another name, a missing pull request, an outcome that is not exactly passed, a permissions ceiling that kills the run before any job starts. Both agent workflow headers now point at it, since being scattered was the original problem.

Every output name in it was checked against setOutput in operations.ts and against the outputs: block in action.yml — an undeclared output silently reads as empty.

06 Ships fine without these

Deferrable because 0.0.1 signals "first cut," and because each is fixable later without touching consumer-owned content.

  • The trust boundary itself. The insecure shape lives outside the custom regions, so a later two-job split propagates to every installation through update. That path is now actually available: with the credential reaching a region under an Octestra-owned name, the split no longer has to edit anything a consumer wrote.
  • SHA-pinning template actions, and pinning the installer's own download. Do it before anyone security-reviews this; not a correctness issue for 0.0.1.
  • A committed working agent example. Would move adoption more than anything else listed, but the commented Claude Code block gets a first consumer moving.
  • SECURITY.md, CONTRIBUTING.md, dependabot, repo description. Public-repo hygiene; no bearing on whether 0.0.1 works.
  • Loops (TODO §1). Correctly deferred, and not a gap in what ships: the seams are held open, the design questions are about autonomous task creation, and the scheduling itself is a cron over operations that already exist.
  • Stale TODO §4 bullet claiming config.yml is regenerated; install.sh:815 already preserves it. Thirty seconds, contributors only.
  • The iOS-specific default validation prompt. lifecycle-validation.md.hbs ships an instruction to run Simulator and XcodeBuildMCP. Prompts are consumer-owned and meant to be edited, so this is not wrong — but one repository's policy is currently the framework's default.
